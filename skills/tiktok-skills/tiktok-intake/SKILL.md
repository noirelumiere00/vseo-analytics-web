> （`scripts/…` はこのスキル、`../tiktok-deck/…` は資料化スキル）。
# ⓪ 受付モジュール（会話の入口）

**営業の工数を最小にすることが、このモジュールの唯一の役目。**
聞けば聞くほど営業は止まる。だから原則はこれ。

> **聞くのをやめて、埋めて見せる。** 質問は思考コストを課すが、
> 候補が埋まっていれば営業は「そのまま」か「ここだけ違う」で済む。

そして初訪ではもう1つ。

> **初訪は選ばせる。書かせない。** 自由記述は書く人によって中身も質もぶれる（2026-09 上長FB）。
> 初訪の入力は選択肢と事実（社名・ID・日付）だけにし、**自由記述は case.json にも資料にも流さない**。

## 起動したら最初に確認すること

依頼が**依頼票の形**で来ているか、**一文の相談**で来ているかを見分ける。

| 来た形 | やること |
|---|---|
| 依頼票（`対象ブランド：`等を含む） | `intake_form.py` に丸ごと渡す → ターン1へ |
| 一文の相談 | そのまま `route_sales_request.py` に渡して型を推定 → ターン1へ |
| 「初訪資料作って」だけ | 対象ブランド・**業種（3択）**・**競合（1社以上。未確認なら「想定」で可）**を1回で聞く。フォーム（`form/intake-form.html`）を渡してもよい。それ以外は聞かない |

## フォルダは2本立てになる（先に知っておくこと）

1つの案件で、置き場所が2つに分かれます。ここを取り違えると、
「取得したのに資料に出ない」「計測したのに反映されない」が起きます。

| | 何を置くか | 誰が使うか |
|---|---|---|
| **run-dir**（作業フォルダ） | 取得した動画・抜いたコマ・計測結果 | ① 取得 と ② 計測 |
| **案件フォルダ**（case-dir） | `case.json`・`raw/*.json`・`INPUT.md`・出来上がった資料 | ③ 資料化 |

繋ぎ方はこうです。

- ① が取った検索結果の JSON は、**両方に置きます**（run-dir と 案件フォルダの `raw/`）
- ② の計測結果を資料に載せるときは、③ で `--analyze-run <run-dir>` を渡します
- 渡さなくても資料は作れます。その場合は「計測していない」と付録に出ます

**初訪は案件フォルダだけで完結します。** 検索結果（`raw/`）・カバー画像（`assets/covers/`）・
ラベル（`labels.json`）・資料（`output/`）・前日チェック（`review/`）がすべて案件フォルダに入り、
計測の run-dir は使いません。

どちらも場所は自由ですが、**案件ごとに1組**にしてください。
別案件の run-dir を混ぜると、古い計測が新しい資料に載ります。

## ターン0：依頼票（営業の手間を0に近づける経路）

営業が最初からこれを貼れるなら、会話はほぼ不要になる。
**空欄があってよい。空欄はAIが調べる**（競合だけは調べて決めない。未定のまま1回だけ聞く）。

```
対象ブランド：
対象商品：
公式サイトURL：
公式TikTokアカウントURL：（無ければ「無し」）
一般検索キーワード：
作りたい資料／章：
希望形式：PPTX
指示：この内容で資料を作成してください
```

`希望形式` の既定は PPTX だけ（PDF は変換できる環境でだけ後から作る）。
`作りたい資料／章` は**型の名前（初訪／具体提案／構成提案／レポート／競合差再提案。①〜⑤ の番号も可。
複数なら「、」で）だけ**を読む。`4-4` のような章の番号は型ではないので、
型は依頼文から推定して確認する（章の番号を書かれたら、その旨を警告に出す）。

初訪は選択式の依頼票になる（`python3 scripts/intake_form.py --template 初訪`）。

```
対象ブランド：ミナトマート
作りたい資料／章：初訪
対象ブランド略称：ミナト                      ← 6字まで。資料の見出しに入る
宛名：株式会社ミナトマート 御中
業種：食品・飲料（food）                      ← 食品・飲料／美容・コスメ／汎用 から1つ（必須）
カテゴリ名：冷凍食品                          ← 1つだけ。この語で検索する
競合1：ヒカリストア（ヒカリ）｜確認済み｜@hikaristore_official
競合2：ソラマート｜想定                       ← 公式IDが分からなければ空欄（AIが調べる）
競合の検索のしかた：{社名} {カテゴリ}          ← 既定。「{社名}」だけも選べる
自社の検索：する                              ← しない なら自社の枠は主張しない版
公式TikTokアカウントURL：@minatomart_official  ← @ID／無し／不明
注力商品1：冷凍餃子                            ← 任意・1〜3
訪問日：2026-10-06                            ← 任意。前日に生成して見る
前日レビュー担当：山田                         ← 任意
希望形式：PPTX
```

**競合は1行1社**：`競合N：正式名（略称）｜確認済み または 想定｜@公式ID または 無し`。
区切りは `｜`。略称・公式IDは省略できる。「確認済み」と書かれていない社は**想定**として扱う。

テンプレは `python3 scripts/intake_form.py --template`（初訪は `--template 初訪`）で出せる。
入力用の1画面フォーム（コピーボタン付き・外部ファイルを読まないのでオフラインでも開ける）は
`form/intake-form.html`。初訪を選ぶと自由記述の欄（目的・指示・一般検索キーワード等）が消え、
業種・カテゴリ（候補チップ付き）・競合4行（業種別の候補チップ付き）・公式TikTok（3択）・
注力商品・訪問日の選択欄に切り替わる。

受け取ったらそのまま渡す。**自分で解釈し直さない。**
貼られた依頼票は、まず **Write ツールで `<run-dir>/request.txt` にそのまま保存**してから `--file` で渡す。
`--text "<貼った文>"` でシェルに埋め込まない（依頼票の `"`・`$`・バッククォートでクォートが壊れ、
`予算は$5000以内` が `予算は000以内` に化ける。コマンドが実行される恐れもある）。

```bash
python3 scripts/intake_form.py --file <run-dir>/request.txt --run-dir <run-dir>
# 初訪は case.json の下書きも同時に作る（既存の case.json は上書きせず case.draft.json に書く）
python3 scripts/intake_form.py --file <run-dir>/request.txt --case-json <案件ディレクトリ>
# Write ツールが使えないときは、クォート付きのヒアドキュメントで標準入力から渡す（中身は展開されない）
python3 scripts/intake_form.py --file - --run-dir <run-dir> <<'EOF_REQUEST'
<貼られた依頼票そのまま>
EOF_REQUEST
```

`作りたい資料／章` に型が複数書かれていれば（`初訪、競合差再提案`）、`statuses` に全部入り、
`generate_modes` に generate.js の `--mode` に渡す値が資料1本につき1つ出る（初訪は必ず単独）。

`--case-json` が書くのは選択肢と事実だけ: `client.short`・`category`・`vocab`・
`brands[]`（`short`・`query`＝既定「{社名} {カテゴリ}」・`file`・`official`・`official_status`・
`confirmed_by_client`）・`keywords[]`（カテゴリ名が `primary`）・`focus_products`・`visit_date`・
`project.recipient`・`first_visit.window`（既定 カテゴリ30／競合20／自社20）・`media_accounts: []`。
**分からない値は書かない**（推測で埋めない）。`acquired_on` は取得した日に入れる。
`official_status` は `@ID → confirmed`／`無し → none`／`不明・空欄 → unknown`。

表記ゆれの当て込みが壊れていないかは `python3 scripts/intake_form.py --selftest` で確かめられる
（「競合の検索のしかた」が「競合」に吸われない、等）。

出力は3つに分かれる。**この分類を崩さないこと。**

| 分類 | 意味 | 対応 |
|---|---|---|
| ✅ 先出し済み | 営業が書いた | **絶対に聞き返さない** |
| 🤖 AIが調べる | 公式サイト・Web検索・取得データから候補が出せる | 聞かずに候補を作る |
| ⛔ 聞くしかない | TikTok側に存在しない社内情報／担当者によってぶれる選択 | ここだけ質問する（1回にまとめ、返事を待たずに進める） |

初訪で ⛔ になるのは **業種（3択）** と **競合（0社のとき）** の2つだけ。
カテゴリ名と公式TikTokは 🤖（公式サイト・Web検索で候補を出す）。

初訪以外で ⛔ になるもの（空欄なら）:

| 型 | ⛔ 聞くしかない |
|---|---|
| 構成提案 | 目的とCTA／尺・本数・必須／禁止表現（status-output-spec の必須入力。推測で埋めると別の資料になる） |
| レポート | 施策開始日／対象期間／施策前スナップショット（「ない」は答え。聞き返さない） |
| 競合差再提案 | 競合（1社以上）／再提案の背景 |

**競合はどの型でも 🤖 にしない**（AIが黙って決めない）。依頼票に「競合：任せる」と
書かれたときだけ、候補を出して「想定」として確認に載せる（`competitors_delegated: true`）。

### `公式TikTokアカウントURL：無し` は「不明」ではない

**「無し」は確定した事実**として扱う。探し直さない。
初訪では資料の「足りていない発信」ページで対象ブランドの枠を「まだ無し」として示せる。
逆に **「不明」の社について「公式0本」とは書かない**（`official_status: unknown`。
0本と言えるのは `confirmed` か `none` の社だけ）。

## ターン1：型を推定して、聞かずに候補を埋める

### ① 作る資料の型は推定する（選ばせない）

`tiktok-analyze/scripts/route_sales_request.py` に推定エンジンがある。**必ずこれを使う。**

```bash
# 一文も依頼票と同じく、シェルに埋め込まず標準入力で渡す（--request を省くと標準入力を読む）
python3 ../tiktok-analyze/scripts/route_sales_request.py <<'EOF_REQUEST'
<営業の一文>
EOF_REQUEST
```

| `needs_clarification` | 対応 |
|---|---|
| `false` | **型の質問をしない。** 推定結果で進め、ターン2の確認に混ぜる |
| `true` | `clarification_question` がそのまま使える。`AskUserQuestion` で5つの型から選ばせる |

実測: 「TOTOに初回訪問で行くけど資料作れる？」→ `初訪 / confidence 1.0 / 逆質問なし`。
「先月やった施策の効果を報告したい」→ `レポート / 0.94`。

初訪の目的は **「現状と競合の発信を見せ、伸びている型をお土産に二次提案へつなぐ」**。
資料は約8枚（表紙 → いま、検索するとこう見える → 競合はこう発信している →
競合がお金をかけて広げている訴求 → 足りていない発信 → いま伸びている型（お土産） →
まずこの3本 → 次回）＋付録2枚。軸は (A) カテゴリで伸びている投稿 と (B) 競合の発信 の2本だけで、
対象ブランド自身の説明には紙面を割かない。深い分析は二次提案（具体提案など）に回す。

### ② 検索キーワードは調べる（聞かない）

営業は**顧客が検索する言葉を知らない**。聞いても答えられないので調べる。

1. 公式サイトを読み、**一般消費者が使うカテゴリ名**を拾う
2. 候補3〜5個を作る（例: TOTO → トイレリフォーム／洗面台 交換／お風呂 リフォーム）
3. ブランド名（A）と一般名詞（B）を1つずつ持つ。**Bが提案材料になる**
4. 迷ったら**候補で取得して件数を見せる**。0件なら検索されていない語だと確定する
   （`search.mjs` は `TIKTOK_TRULY_EMPTY` と `TIKTOK_BOT_WALL` を切り分けるので0件の意味が確定できる）。
   **0件の語は `build_dataset.py --source` にも `case.json` の keywords／brands にも入れない**
   （0件のファイルが1つでもあると、データ化・INPUT.md 作成・初訪の組み立てが止まる）。
   ターン3の発見として「◯◯は検索されていない語でした」と伝え、別の候補に替える

**初訪ではカテゴリ名を1つだけ決める。** それが主キーワード（`keywords[].primary`）になり、
競合も「{社名} {カテゴリ}」で検索する。カテゴリ名を2つ以上にしない（軸がぼける）。

### ③ 競合

**初訪では競合は必須（軸B）。1社以上、2〜4社を推奨。** 資料の半分（競合はこう発信している／
お金をかけて広げている訴求／足りていない発信）が競合から出るので、無いまま作らない。

- 競合の選定は営業の仕事。**⛔ として1回だけ聞く**（ターン2の確認にまとめる）
- クライアントに確認できていなくても止めない。**「想定」のまま進める**
  （`brands[].confirmed_by_client: false`）。資料には「※競合は弊社の想定です。ご確認ください」が入り、
  最後の「次回」ページで確認する
- 営業が「分からない」「任せる」と言ったときだけ、フォームの業種別候補か Web検索から
  候補を出し、**想定**として確認に載せる。黙って決めない
- 競合は「{社名} {カテゴリ}」で検索する（`競合の検索のしかた` で「{社名}」だけにもできる）

初訪以外の型では従来どおり。競合が決まっていなくても止まらない（競合を使う章が出ないだけ）。
「競合が決まったら章が増えます」と伝えて先に進む。

**検索面から競合を抽出しようとしないこと。** 実測で潰れている。
検索面に出るのは**インフルエンサー個人**で、競合ブランドの公式ではない
（あるEC案件では149件中、認証バッジは4件で全員クリエイターだった）。
ただしその情報は「**誰に頼めばこの面に入れるか**」として別途使える。

### ④ 公式TikTokアカウントも調べる（聞かない）

Web検索と、取得済みデータの認証バッジ付きアカウントとの突合で候補を出す。

**`search.mjs` にアカウント検索モードは無い**（mode は search / comments / download / fetch のみ）。
検索面に出ていない公式は自動特定できないので、その場合だけ短く確認を取る。
「公式が出ていない」と「handleを間違えた」は区別できないため、0本だったときは必ず本人確認する。
確認が取れるまでは `official_status: unknown` のまま（資料で「0本」と言わない）。

### ⑤ 業種は選んでもらう（初訪のみ・推測しない）

業種（食品・飲料／美容・コスメ／汎用）で、投稿の切り口・訴求を分類する語彙
（`../tiktok-deck/tools/vocab/{food,beauty,general}.json`）が決まる。
AIが推測すると担当者ごとに資料がぶれるので、**3択で選んでもらう**（⛔）。

## ターン2：1回にまとめて確認する（★ここでターン数が決まる）

**質問を分けない。** 推定と候補を全部1画面に載せ、**訂正だけもらう**。

```
初訪の資料（約8枚）を作ります。以下で進めます。違うところだけ教えてください。

  作る資料 : 初訪（ご依頼の「初回訪問」から判断）
  業種     : ？ 食品・飲料／美容・コスメ／汎用 のどれですか ← ここだけ選んでください
  カテゴリ : トイレリフォーム（公式サイトから）
  競合     : LIXIL・パナソニック（想定。未確認なら資料に「※競合は弊社の想定です」と入れ、次回ページで確認）
  公式TikTok: 無し ← 事実として扱い、探し直しません
  訪問日   : 10/6 → 前日 10/5 に生成してお送りします
  出力     : PPTX

このまま進めてよければ、取得から資料化まで走らせます。
```

- `AskUserQuestion` を使うなら**1回だけ**。項目ごとに聞かない
- 「違ったら言ってください」の形にする。**返答が無くても止まらない設計**にする
  （初訪なら、返事を待つ間にカテゴリの取得から始める）
- 型を外しても損害は章立ての差だけ。**間違いを恐れて聞き返すほうがコストが高い**

### ④レポートを選んだ場合だけ、ここで必ず聞く

自動導出が**原理的に不可能**な3つ。TikTok側に存在しない社内情報。

```
効果検証は施策前のデータが無いと前後比較が作れません。あとから遡れません。

  ・施策開始日はいつですか？
  ・報告する期間はどこからどこまでですか？
  ・施策を始める前の検索面の記録はありますか？
    まだ施策を始めていないなら、今日のうちに記録だけ取っておくべきです
```

取得できたら `build_dataset.py` に渡して記録する（`confirmed_config.json` に残る）。

```bash
--campaign-start 2026-08-01 --period "2026-08-01..2026-08-31" --baseline <施策前のrun-dir>
```

**レポート資料は、いまのツールでは最後まで自動では通らない前提で扱う。** 正直に伝えること。

- 章 5-4（定点観測）は対象外（`modules.json` の excluded）。施策前データを渡しても章は増えない
- `node src/generate.js --mode レポート` は、施策前後を比べられる状態でないと止まる
  （施策前の基準が INPUT.md に無い、または前後比較のページが未実装。偽の効果測定を作らないため）。
  レポートを約束する前に、実際に `--mode レポート` で止まらないかを確かめる
- 止まったら、営業に「施策前後の比較資料はまだ自動で作れない」と伝え、
  現状値だけの資料（例: `--mode 具体提案`）にするかを確認する。**施策前後の比較・効果測定とは書かない**
- 施策前データが「ない」と答えられたら、それは確定した事実（聞き返さない）。前後比較は作れない
- それでも3点は必ず聞き、施策前スナップショットは今日取る（あとから遡れない。比較は後で手作業でもできる）

## ターン3：走らせて、発見を先に返す

キーワードが1つ決まれば動ける。**全部揃うのを待たない。**

```bash
python3 scripts/gaps.py --status 初訪 --case <案件ディレクトリ>     # 初訪
python3 scripts/gaps.py --run-dir <run-dir> --status 具体提案        # 初訪以外
```

初訪では、案件フォルダに `labels.json` があれば
`../tiktok-deck/tools/build_first_visit.py --case <案件> --dry-run --json` を呼び、
**ページごとの成否**（✅ そのまま／△ 縮めて出す／✗ 出さない＋理由、⛔ 止まっている理由）を返す。
ラベル前や case.json が無い段階では、**初訪の必須入力と工程のチェックリスト**
（業種・カテゴリ・競合・公式・取得・カバー・ラベル）と、次に打つコマンドを返す。
初訪は旧 `modules.json` の 1-1〜1-6 には対応させない。

初訪以外の出力は**そのまま営業に渡せる3部構成**。

1. **データを見て気づいた点** — 提案の切り口。**これを先に出す**
2. **いま数えられる章** — 実数つき。足りなくても分析は進められると伝える
3. **足りないもの／次の一手** — なぜ必要か・**営業に聞く**（営業しか知らない事実だけ）・
   **こちらで実行**（計測やコマ抽出など。営業に「実行してよいですか」とは聞かない）・この入力を使う章

**章ID（1-1〜6-3）は `build_deck.py`／`modules.json` の分析の番号で、generate.js が作るPPTXのページ
（Q1〜Q8 等）とは対応していない。** 「1-1 が出せます」を「資料に1-1のページが載る」と言い換えない。
資料のページ構成は `generate.js --mode <型>` が決める。

`--status` は generate.js と同じ別名も受ける（quick=初訪、deep/full/提案=具体提案、構成=構成提案、
競合差/再提案=競合差再提案、report/効果測定=レポート）。知らない名前や `build_deck.py` が止まったときは
**[STOP] で止まる**（前回の結果を出し直さない）。`--run-dir` に `intake.json` があれば、
「公式TikTok：無し」「施策前データ：ない」を確定事実として扱い、聞き返さない。

**発見を先に出す。** 不足だけ言われると営業は止まるが、
「写真投稿が62.8%」「広告（#PR表記か広告フラグ）は再生2.4倍なのに保存率0.84倍」のような事実が来ると会話が前に進む。

### 初訪の資料化（訪問の前日に生成する）

コマンドは `../tiktok-deck` で実行する（`npm install` は初回だけ）。`<案件>` は案件ディレクトリ。

1. **case.json** — `python3 scripts/intake_form.py --file 依頼票.txt --case-json <案件>`（受付側で実行）
2. **取得** — tiktok-acquire の `search.mjs` で、`--case-json` が表示した検索語を `case.json` の `file` に保存する
   - カテゴリKW（主キーワード。表示順の上位30本を使う）
   - 競合を「{社名} {カテゴリ}」で1社ずつ（上位20本＋PR投稿を使う）
   - 任意で自社を「{社名} {カテゴリ}」（`自社の検索：しない` なら取らない）

   ```bash
   node search.mjs --query "冷凍食品" --max 50 --out <案件>/raw/kw_冷凍食品.json
   node search.mjs --query "ヒカリストア 冷凍食品" --max 50 --out <案件>/raw/brand_ヒカリストア.json
   ```
   件数は `--max 50` を目安に（競合のPR投稿を多く拾いたいときは増やす）。
   表示順を語るので `--sessions` は1のまま。CAPTCHA が出たら止めて人に報告する。
   取れた日を `case.json` の `acquired_on`（YYYY-MM-DD）に入れる
3. **カバー画像** — `python3 tools/fetch_covers.py --case <案件>`
4. **ラベルの下地** — `python3 tools/label_posts.py --case <案件> --init` → `--options`（選べる値）→ `--contact`（一覧シート）
5. **★ AIが画像を見て選ぶ** — 一覧シートを実際に開き、1投稿ずつ関連性・切り口・訴求を
   **`--options` に出た語彙の中からだけ**選んで patch に書く（形式は `--options` の表示に従う）。
   見ていない投稿を確定しない。迷ったら「要確認（unsure）」。語彙に無い言葉を作らない
6. **反映と検査** — `python3 tools/label_posts.py --case <案件> --apply patch.csv` → `--check`
7. **組み立て** — `python3 tools/build_first_visit.py --case <案件>`
   （途中で `scripts/gaps.py --status 初訪 --case <案件>` を打つと、何ページ出せるかが先に分かる）
8. **生成** — `node src/generate.js --case <案件> --mode 初訪`
   → `<案件>/output/TikTok_Competitive_Research_初訪.pptx`
   **初訪は単独の資料。** `--mode "初訪,…"` は止まる。二次提案は `--mode 具体提案` 等で別ファイルにする
9. **検査** — `python3 tools/preflight.py <案件>/output/TikTok_Competitive_Research_初訪.pptx` と
   `python3 tools/verify_assets.py --case <案件>`。通らないものは出さない
10. **前日レビュー** — `<案件>/review/初訪_前日チェック.md`（選択式のチェックリスト）を、
    **訪問の前日**に担当者（`前日レビュー担当`）が一通り見てから当日持っていく

### 初訪以外の資料化と PDF

コマンドは `../tiktok-deck` で実行する。**3つとも同じ `--case` を渡す**（`generate.js` は `--case` が無いと
スキルのフォルダ自身を案件とみなし「INPUT.md がありません」で止まる）。

```bash
cd ../tiktok-deck && npm install            # 初回だけ
# 計測（tiktok-analyze の measure_keywords.py）をした案件は --analyze-run <run-dir> を必ず渡す。
# 渡さないと、run-dir が案件フォルダの外にある場合は「計測していない」扱いになり、計測結果が資料から消える。
# 計測していない案件では付けない（measurement/measure_output.json が無いと [致命的] で止まる）
python3 tools/build_input_md.py --case <案件ディレクトリ> --analyze-run <run-dir>
python3 tools/merge_authored.py --case <案件ディレクトリ>
node src/generate.js --case <案件ディレクトリ> --mode <ステータス名>
```

**generate.js は PPTX だけを出す（`--pdf` オプションは無い。付けても PDF はできない）。**
`希望形式` に PDF が含まれていたら、PPTX のあとで変換を試し、**PDF ができたかを必ず確かめる**。

```bash
soffice --headless --convert-to pdf --outdir <案件>/output <案件>/output/<資料>.pptx
ls <案件>/output/<資料>.pdf     # 無ければ失敗
```

LibreOffice（`soffice`）が無い・変換に失敗した環境では、**その旨と PowerPoint の
「ファイル→エクスポート→PDF」の手順を伝える**。成功したフリをしない。

## 後続モジュールへの引き継ぎ

| 決まったこと | 渡す先 |
|---|---|
| 検索キーワード・競合 | `tiktok-acquire` → `search.mjs --query`（初訪は `case.json` の `keywords[].query`／`brands[].query` を `--out <案件>/<file>` で） |
| 初訪の入力（業種・カテゴリ・競合・公式・注力商品・訪問日） | `intake_form.py --case-json` → 案件の `case.json` → `tiktok-deck` の初訪パイプライン |
| 型（初訪等） | `tiktok-deck` → `node src/generate.js --case <案件> --mode <ステータス名>`（intake の `generate_modes` を1つずつそのまま渡せる。**初訪は単独**。複数は初訪以外で `--mode "具体提案,構成提案"`） |
| ブランド・商品・公式URL | `tiktok-analyze` → `build_dataset.py --brand --product --official-*`（「公式：無し」を渡す引数は無い。`intake.json` を run-dir に置けば gaps.py が聞き返さない） |
| 施策開始日・期間・施策前データ | `tiktok-analyze` → `build_dataset.py --campaign-start --period --baseline`（記録されるだけ。レポート資料の生成条件は上の「④レポート」を参照） |

**注意**: `route_sales_request.py` の `requested_modules` は `modules.json` の `1-1`〜`6-3` と
対応表が無い。**使えるのは `status_name` だけ。** `--modules` にそのまま渡さないこと。
初訪の `requested_modules`（`current_search_view`／`competitor_communication`／`competitor_paid_push`／
`posting_gap`／`category_winning_types`／`first_three_ideas`）は、初訪資料のページ
（いま、検索するとこう見える／競合はこう発信している／お金をかけて広げている訴求／
足りていない発信／いま伸びている型／まずこの3本）の呼び名で、`first_visit.json` の
ページ id（now／competitors／paid／gap／winning／plans）に対応する。

## この受付でやってはいけないこと

| 禁止 | なぜ |
|---|---|
| 最初に検索キーワードを聞く | 営業は答えられない。公式サイトを読めば候補は作れる |
| 型を選ばせるために1ターン使う | `route_sales_request.py` が推定できる。`needs_clarification` が false なら聞かない |
| 競合を黙ってAIが決める | 競合の選定は営業の仕事。初訪は1回だけ聞き、未確認なら「想定」と明示して進める |
| 初訪で業種をAIが推測で決める | 分類の語彙が決まる選択。推測すると担当者ごとに資料がぶれる。3択で選んでもらう |
| 初訪で自由記述（目的・指示）を case.json や資料に流す | 書く人で質がぶれる。流してよいのは選択肢と事実（社名・ID・日付）だけ |
| 初訪を他の型と1つの資料にまとめる | 初訪は約8枚のお土産。二次提案は別ファイル（`--mode "初訪,…"` は止まる） |
| 画像を見ずにラベルを確定する／語彙に無い言葉でラベルを付ける | 無関係な投稿が例に載る事故の原因。見たものを語彙から選ぶだけ |
| 項目ごとに質問を分ける | ターンが増える。1回にまとめて訂正だけもらう |
| 情報が全部揃うまで取得を始めない | KWが1つ決まれば動ける。待つほど価値が減る |
| `公式TikTok：無し` を「不明」として探し直す | 無いことが確定した事実 |
| 「不明」の社について「公式0本」と書く | 0本と言えるのは confirmed か none の社だけ |
| ④レポートで施策前データの確認を飛ばす | 遡れない。最も取り返しがつかない |
| 検索面の投稿者を競合として扱う | 実測で個人クリエイターだった。競合ブランドではない |
| PDF変換の失敗を黙って飲む | 営業は PDF が出たと思って商談に行く |
| 貼られた依頼票を `--text "…"` でシェルに埋め込む | `$`・`"` で中身が化ける／コマンドが実行される。ファイルに保存して `--file` |
| 0件の語を case.json や `--source` に入れる | 取得・組み立てが止まる。「検索されていない語」という発見として伝える |
| 不足だけ報告して終わる | 「いま出せること」と「発見」を必ず添える |
